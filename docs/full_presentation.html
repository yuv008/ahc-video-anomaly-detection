Slide 1 · The problem

Detect anomalies in drone/CCTV/dashcam video, in real time, on a GPU too small for a big model Accidents, fire, flooding, fighting, loitering and 7 other classes — spotted by a small vision-language model running across many feeds at once, never a hosted large model at inference.

Locked constraints

Runtime target: free Tesla T4 — 16GB, Turing SM75, fp16 only (no usable bf16)
Objective: score against a private evaluation set, judged by an undisclosed IoU/weighting formula
Output: a list of timestamped events per video — not one verdict per video
Real-time: the model must keep pace with the video, per feed, on the same limited GPU

Slide 2 · Data analysis, not assumption

The dataset has a built-in trap: training clips are pre-trimmed, test videos are not Every architecture decision downstream exists because of this one mismatch.

Train vs. test event coverage

Train clipsTest L1Test L2Test L3
Duration5–30s5–26s240s308–629s
Event coverage~99.9%~100%~7.7%~7.7%
Max event length30s26s60s125s

A model trained naively learns the shortcut "a clip was shown to me ⇒ an anomaly is present" — true ~100% of the time in training. Deployed on long footage, it fires almost continuously. This mismatch, not model capacity, was the dominant risk from day one.

Other findings that shaped the build

7.3:1 class imbalance — 973 normal clips vs. 77 fire clips
Supervision is boilerplate — loitering's 300 clips share ONE description string. Build a classifier, not a captioner.
Multi-event, multi-class videos — one test video holds 4 different anomaly types back to back
Level 2 is stitched, Level 3 is not — L2 timestamps are suspiciously round; L3 has a 125s event longer than any training clip ever seen

Slide 3 · The shipped pipeline

Two models and a CPU-only aggregator — nothing large runs at inference A small VLM decides windows; a second model's confidence filters false alarms; a cheap aggregator turns both into events.

STAGE 0Window sampler 4s windows, no overlap, 8 frames. Measured: 50% overlap is strictly dominated — same F1, worse boundary IoU, 2× compute. no model · CPU
STAGE 2Qwen3-VL-8B classifier 4-bit, LoRA r=32, fp16. Emits {is_anomaly, class_name}; scores read from token logprobs, not the string. ~4.3s / window on T4
STAGE 2.5Cosmos confidence gate A second model VETOES Qwen's positive calls it isn't itself confident (≥0.95) about — post-hoc filter, not a second classifier. ~2.0s / window · shipped
STAGE 3Temporal aggregator Hysteresis + merge-gap + midpoint boundary refinement turns window verdicts into a clean event list. no model · CPU · free to re-tune

What is deliberately not here

No Stage-1 pre-classification gate. Real-time turned out to be achievable without one — several configurations clear the 4-second-per-window budget on a single feed outright, once the resolution cap and no-overlap window fix were measured and applied. Its only remaining value would be running more feeds per GPU, a throughput question the brief doesn't require solving.

Slide 4 · Model selection, measured not assumed

Three assumptions broke under measurement — each one would have shipped a worse system Every number below came from running the model on the actual target hardware, not from a spec sheet.

assumption broke

"Smaller = faster"

Qwen2.5-VL-3B measured slower than the 7B at every matched config (2.23s vs 3.11s/window). The 3B is 36 layers deep vs the 7B's 28 — depth dominates latency at batch 1, not parameter count. Verified A→B→A to rule out thermal drift (0.3%).

assumption broke

"bf16 is safe on any GPU"

is_bf16_supported() returns True on a T4 — but that counts emulation. Real throughput: fp16 20.98 TFLOP/s vs bf16 2.28 TFLOP/s. Picking bf16 would have made training 9× slower, silently.

lever found

Resolution, not frame count

Uncapped 720p costs 1,196 vision tokens/frame → 17.8s/window. Capping to 256 tok/frame is a 5× speedup at the identical frame count — the single biggest lever in the whole latency budget.

Final pick: Qwen3-VL-8B-Instruct, 4-bit, LoRA r=32

Every top team on the public AI City 2026 Track-3 leaderboard runs a ~8B Qwen VLM. Qwen3.5 (used by the #1 team) was rejected on tooling, not merit — no 4-bit build exists for the trainer we use, and the leaderboard gap to Qwen3-VL-8B is 0.0009, noise-level. SigLIP and Cosmos-Embed1 were also evaluated as the primary classifier and rejected — see slide 6.

Cosmos-Embed1 as a classifier fails badly — as a confidence gate on Qwen, it's the whole win Same model, two claims tested separately. Only one survived contact with the platform.

failed live

Cosmos AS the Level-1 classifier

Measured standalone: L1 0.617 vs Qwen's 0.550 — better on both binary accuracy (0.833 vs 0.750) and class accuracy. Looked like a clean win.

Uploaded anyway — score dropped. Cosmos fires on 22/24 L1 videos (vs Qwen's 14/24) and wrecked 3 of 4 ground-truth-normal videos with false alarms the local metric didn't weight heavily enough.

This was the third time a local-only improvement failed on upload. Lesson now load-bearing: check matched-event count and false-alarm count directly — never trust the local score alone.

Slide 7 · The deepest finding

Localization is solved. Naming the class correctly is the entire remaining ceiling Found by testing an unsupervised, zero-training baseline against the shipped model — on the exact same windows.

What's actually happening inside real events

True classModel fires?Correct?
traffic_congestion100%100%
traffic_accident10%0%
loitering0%0%

62% of windows inside real events are silent or wrong. No amount of threshold tuning lifts a ceiling set upstream of aggregation — confirmed by testing a decoupled localize-then-vote design that changed nothing.

Isolating the two halves of the problem

Unsupervised novelty score (zero params, zero training — just "how different is this window from the rest of its own video"): AUC 0.864 for traffic_accident vs. normal, where the fine-tuned model scores 0/79 on the same windows.
Novelty localization + oracle-known class → 8 matched events, overall 0.669 — vs. the shipped pipeline's 1 match, 0.400.
Root cause: trained on 560 of 14,157 labelled windows available — about 4%. The synthesized long-form dev set built specifically for this mismatch was never used in training.
